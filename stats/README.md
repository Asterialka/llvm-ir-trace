# Результаты эксперимента

Для эксперимента запустил «Игру жизни» на поле 64 × 48: 64 шага, seed 42. Собрал трассы для `-O2` и `-Os` на LLVM/Clang 22.1.8. Отрисовка шла через SDL с драйвером `dummy`, чтобы запуск не зависел от наличия дисплея.

В трассу попала только логика из `app.c`: инициализация поля, обновление клеток, подготовка пикселей и подсчёт контрольной суммы. User `phi` пропускались, но `phi` могли выступать операндами других инструкций.

## Что получилось

| Показатель | `-O2` | `-Os` |
|:---|---:|---:|
| Инструкций в оптимизированном IR | 235 | 141 |
| Пропущено User `phi` | 12 | 14 |
| Выполнено инструкций без `phi` | 9 715 071 | 9 897 791 |
| Связей `User <- Operand` в трассе | 13 307 441 | 13 588 529 |

Одна инструкция может использовать несколько других, поэтому связей получилось больше, чем исполненных инструкций. Повторный операнд учитывался отдельно для каждой позиции.

Контрольная сумма во всех сборках, включая версии без инструментирования, совпала: `a2efe1ef278eaa64`.

## Частые паттерны

Для каждой длины окна от 1 до 5 выбрал самый частый паттерн использования. Окна перекрываются и идут по всей трассе, включая переходы между блоками и вызовами функций.

| Длина | Паттерн | Частота `-O2` | Частота `-Os` |
|---:|:---|---:|---:|
| 1 | `getelementptr <- getelementptr` | 2 046 806 | 2 050 646 |
| 2 | `load <- getelementptr; zext <- load` | 1 575 936 | 1 575 936 |
| 3 | `load <- getelementptr; zext <- load; add <- add` | 1 179 648 | 1 179 648 |
| 4 | `load <- getelementptr; zext <- load; add <- add; add <- zext` | 1 179 648 | 1 179 648 |
| 5 | `add <- zext; getelementptr <- getelementptr; getelementptr <- and; load <- getelementptr; zext <- load` | 983 040 | 983 040 |

Эти паттерны в основном возникают в `app_step`. Для каждой клетки нужно прочитать восемь соседей и сложить их значения. Сначала вычисляется адрес строки и клетки, затем выполняются `load`, расширение значения из `i8` в `i32` через `zext` и сложение. Накопленная сумма и очередной сосед дают связи `add <- add` и `add <- zext`.

Связь `getelementptr <- and` появляется при вычислении индексов соседей: ширина поля равна 64, поэтому остаток от деления заменяется маской 63.

Отдельно посчитал окна в последовательности самих инструкций. Здесь каждая выполненная инструкция даёт один элемент, независимо от числа операндов.

| Длина | Паттерн | Частота `-O2` | Частота `-Os` |
|---:|:---|---:|---:|
| 1 | `getelementptr` | 2 065 334 | 2 075 318 |
| 2 | `getelementptr; load` | 1 777 238 | 1 801 814 |
| 3 | `getelementptr; load; zext` | 1 575 936 | 1 575 936 |
| 4 | `getelementptr; load; zext; add` | 1 376 256 | 1 376 256 |
| 5 | `add; getelementptr; load; zext; add` | 1 179 648 | 1 179 648 |

В обоих режимах лидируют одни и те же последовательности. Их частоты часто совпадают, поскольку основной цикл обработки соседей выполняет одинаковую работу.

## Разница между `-O2` и `-Os`

При `-Os` в модуле на 40% меньше IR-инструкций. При этом за весь запуск у `-O2` выполнилось примерно на 1,85% меньше инструкций и на 2,07% меньше связей использования.

Основную разницу даёт `app_pixels`: 307 328 выполненных инструкций при `-O2` против 464 000 при `-Os`. В варианте `-O2` LLVM разворачивает цикл обработки строки и использует векторные загрузки и записи. Тело функции получается больше, зато реже выполняются инструкции управления циклом.

Это сравнение числа событий в LLVM IR. Время выполнения не измерялось, а векторная инструкция считается одним событием, поэтому по этим числам нельзя напрямую сравнить скорость сборок.

Полные таблицы лежат в [O2](O2) и [Os](Os): `uses.tsv` — паттерны использования, `instructions.tsv` — паттерны инструкций, `summary.tsv` — сводка.

Повторить эксперимент можно командой `make stats` из корня проекта. При другой версии LLVM частоты могут измениться.
